# Стандарты проекта

## Обзор
Этот документ определяет стандарты кодирования и практики разработки для этого проекта.

## Общие и обазятаельные правила для всех агентов
- Не расписывай "Преимущества использования" подходов, способов, методов и т.д. без явной просьбы указать или расписать их. В большинстве случаев это абсолютно неинформативные данные.

## Стандарты по оформлению кода
- Язык только C++, вставки чистого C кода нежелательны.
- Для кастов лучше использовать явных и читаемых конструкций (static_cast, reinterpret_cast, и т.д.) 
- Не используй int, unsigned int и подобные неявные, архитектурнозависимые типы. Используй всегда типы с понятной размерностью, такие как uint8_t, int32_t и подобные.
- Использовать snake_case нотацию, аналогично используемую в языке Python.
- Разделять источники (.h) и реализацию (.cpp) для файлов.
- Использовать Header Guards вместо #program once.
- При описании классов лучше сначала описать переменные (сначала приватные, потом публичные), а потом публичные и приватные методы. 
- Использовать значимые и конкретные имена переменных и функций. Не делать именование общим и неконкретным, название должно в полной мере отображать суть данных и функци. Если получается слишком длинное название, возможно стоит произвести декомпозицию и разбить данные на структуры, а процедуру на подметоды. 
- Добавлять комментарии для сложной логики. Оформление комментарием должно быть СТРОГО в стиле Doxygen.
- При добавлении нового функционала и работе с QT модулями, компонентами обязательно загружай документацию и используй её при разработке. Используй версию Qt 6.9.2 или Qt 6.10.
- Не используй реализации на основе QT QML, лучше все делать нативно в стиле С++.
- Для комментариев, документации, Markdown файлов обязательно используй русский язык.

### Правило использования модификатора final

**Принцип:** Все конечные реализации классов должны быть помечены модификатором `final` для применения верных оптимизаций компилятором (devirtualization).

**Правило:** 
- Все конкретные реализации (классы, которые используются напрямую) **ДОЛЖНЫ** иметь модификатор `final`
- Объекты классов БЕЗ модификатора `final` можно использовать ТОЛЬКО если:
  - От них происходит наследование (промежуточные абстрактные классы)
  - Они не используются напрямую, а служат только базой для других классов
- Единственное исключение: объекты классов без `final` можно создавать при написании тестов

## Система сборки и исполнения программ, скриптов
- CMake — основная система сборки, которая использует подмодули сборки QT.
- Целевая платформа запуска приложений и скриптов: Windows (win32), однако модули отвечающие за обработку сигнала в основном предназначаются для микроконтроллеров ESP32.
- Учитывай, что ты должен писать команды для power shell. Многих утилит из linux может не быть.

- Проверьте утечки памяти

## Структура файлов
- В корневой директории для исходных кодов (src) не стоит добавлять какой-то функционал, лучше сделать подмодуль и импортировать его CMakeLists.txt.
- Заголовки модуля лучше хранить в  : `src/*module-name*/include`
- Реализации для заголовков модулей лучше хранить в: `src/*module-name*/`

### Правило соответствия структуры include и src

**Принцип:** Структура папок в `*module-name*/src/` должна точно соответствовать структуре папок в `*module-name*/include/*module-name*/`.

**Правило:** Если заголовочный файл находится в подпапке `include/`, то его реализация должна находиться в соответствующей подпапке `src/`.

**Примеры:**

| Заголовочный файл | Файл реализации |
|------------------|-----------------|
| `include/core/core.h` | `src/core/core.cpp` |
| `include/data_processors/signal_processing/fft_processor.h` | `src/signal_processing/fft_processor.cpp` |
| `include/visualization/renderers_2d/chart_renderer.h` | `src/visualization/renderers_2d/chart_renderer.cpp` |

### Правило организации типов и интерфейсов

**Принцип:** Типы данных, интерфейсы и абстракции модуля (именно общие, которые применяются в модуле повмесместно) размещаются в подпапке `abstract/` внутри `include/module-name/`.

**Структура:**

```
include/module_name/
├── abstract/                       # Типы, интерфейсы, абстракции
│   ├── types.h                     # Типы данных модуля
│   ├── interfaces.h                # Интерфейсы модуля (если файл с типами слишком большой)
│   └── mixins.h                    # Миксины (если требуются)
├── implementation1.h               # Конкретные реализации
└── subfolder/
    └── implementation2.h
```

**Содержимое `abstract/`:**
- `types.h` — структуры, перечисления, константы, типы данных
- `interfaces.h` — интерфейсы (чистые виртуальные классы)
- `mixins.h` — миксины для добавления функциональности

**Правило:** Файлы в `abstract/` содержат только определения (структуры, перечисления, интерфейсы), без реализации.

**Примеры:**

| Заголовочный файл | Назначение |
|------------------|-----------|
| `include/core/abstract/types.h` | Типы данных ядра |
| `include/core/abstract/interfaces.h` | Интерфейсы ядра |
| `include/data_processors/abstract/types.h` | Типы обработчиков |
| `include/data_processors/abstract/interfaces.h` | Интерфейсы обработчиков |
| `include/data_processors/abstract/mixins.h` | Миксины обработчиков |

**Важно:** Типы и интерфейсы НЕ имеют файлов реализации (.cpp). Реализация находится в классах, которые наследуют интерфейсы.

**Когда разделять типы и интерфейсы:**
- На начальном этапе можно размещать всё в одном файле `types.h`
- Разделение на `types.h` и `interfaces.h` требуется когда файл становится >500 строк
- Типы и интерфейсы логически разделяются на несколько групп

## Использование карты проекта

**Карта проекта** (`docs/PROJECT_MAP.md`) содержит подробную архитектурную документацию и должна загружаться в контекст при:

1. **Решении комплексных проблем и задач проекта** — карта поможет быстрее понять общую структуру и компоненты
2. **Добавлении нового функционала** — для определения правильного места интеграции
3. **Отладке сложных проблем** — для понимания потоков данных и взаимодействия компонентов
4. **Работе с новыми модулями** — для быстрого погружения в их назначение и интерфейсы

Карта проекта не дублирует технические детали реализации, а предоставляет высокоуровневое понимание архитектуры. Для конкретных API и деталей реализации всегда обращайтесь к исходному коду.
