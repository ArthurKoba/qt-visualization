# Требования: Архитектура конвейера обработки данных

## Обзор

Разделить текущую архитектуру проекта на три логические группы компонентов:
- **Источники данных** — компоненты, которые производят или захватывают данные извне
- **Обработчики данных** — компоненты, которые преобразуют данные
- **Получатели данных** — компоненты, которые потребляют данные для отображения или передачи
И две служебные:
- **Ядро** — конфигурация системы конвейера обработки данных
- **Сервер агрегации** — компонент для отслеживания работоспособности всех компонентов

## Текущее состояние

### Существующие компоненты

| Компонент | Текущая роль | Описание |
|-----------|-------------|----------|
| `Generator` | Генератор сигнала | Генерирует тестовый синусоидальный сигнал |
| `WASAPILoopback` | Захват аудио | Захватывает системный аудиовыход через WASAPI |
| `SerialPort` | Захват данных | Получает данные от микроконтроллера ESP32 |
| `AudioWindow` | Обработчик | Применяет оконную функцию (Hanning) к сэмплам |
| `FFT` | Обработчик | Преобразует временной сигнал в частотный спектр |
| `Analyzer` | Обработчик + отправитель | Комбинирует FFT, шкалу Bark, whitening, отправляет в графики |
| `Charts` | Визуализаторы | Отображают данные (LineChart, BarChart, FreqChart) |
| `SurfaceGraph` | Визуализатор | 3D спектрограмма |

## Целевая архитектура

### 1. Источники данных (Data Sources)

Компоненты, которые **производят** данные из ничего или **захватывают** их извне.

**Классы:**
- `SignalGenerator` — генерирует синусоиду, шум, другие сигналы
- `AudioLoopbackSource` — захватывает системный аудио (WASAPI)
- `SerialDataSource` — получает данные от ESP32 по последовательному порту

### 2. Обработчики данных (Data Processors)

Компоненты, которые **преобразуют** входные данные в выходные.

**Классы:**
- `WindowSignalCollector` — непрерывно собирает сигналы в окно размером 2**N, для FFT. Делает смещение (удаление) старого сигнала для добавления нового.
- `WindowFunctionsApplier` — восстанавливает сигнал из окна (обратное преобразование)
- `FFT` — преобразует во временную → частотную область
- `SpectralWhitening` — нормализация спектра
- `AmplitudeSpectrumConversion` — преобразование результата FFT в амплитдуный спектр
- `EnergySpectrumConversion` — преобразование результата FFT в энергетические спектр
- `VolumeNormalization` — нормализация громкости по iso226
- `BarkScaleMapper` — преобразует частоты спектра в шкалу Bark
- `MelScaleMapper` — преобразует частоты спектра в шкалу Mel
- `SpectrogramBuilder` — строит из спектра спектрограммы

### 3. Получатели данных (Data Sinks)

Компоненты, которые **потребляют** данные для различных целей.

**Классы:**
- `DataRenderer` — отображает данные на графике (обобщённый интерфейс для всех графиков)
- `ChartRenderer` — отображает 2D график для данных
- `SpectrogramRenderer` — отображает 3D спектрограмму для спектра данных
- `AudioRenderer` — воспроизводит аудио через устройство (в будущем)
- `DataRecorder` — записывает данные в файл (в будущем)

## Потоки данных

### Сценарий 1: Генератор → Обработчики → Визуализация
```
SignalGenerator → WindowSignalCollector → FFT → AmplitudeSpectrumConversion → ChartRenderer
```

### Сценарий 2: Loopback → Обработчики → Визуализация
```
AudioLoopbackSource → WindowSignalCollector → WindowFunctionsApplier → FFT → EnergySpectrumConversion → MelScaleMapper → SpectrogramBuilder → SpectrogramRenderer
```

### Сценарий 3: ESP32 → Визуализация
```
SerialDataSource (BDSP) → ChartRenderer
```

## Требования к взаимодействию

1. **Слабая связанность** — компоненты не должны знать детали реализации друг друга, что требует обязательного использования паттернов ООП и интерфейсов сущеностей (в виде классов)
2. **Гибкость** — возможность подключать/отключать компоненты без изменения кода
3. **Потокобезопасность** — передача данных между потоками и компонентами с помощью очередей
4. **Масштабируемость** — возможность добавлять новые источники/обработчики/приёмники

## Нефункциональные требования

1. Использовать только C++ (без C кода и QML описаний)
2. Соблюсти стандарты проекта (snake_case, Doxygen, header guards)
3. Обновить project-map.md с новой архитектурой

## Архитектура ядра и взаимодействие компонентов

### Ядро приложения (Core)

Основное приложение, которое управляет всеми компонентами:

**Функции:**
- Управление жизненным циклом (их запуск, завершение) всех компонентов (источники, обработчики, получатели)
- Проверка доступности компонентов и автоматический запуск при необходимости
- Управление соединениями между компонентами
- Поддержка двух режимов работы:
  - **Графический режим** — с UI для визуальной настройки и отображения
  - **Консольный режим** — без UI, быстрая сборка и запуск


### Связывание компонентов

**Правила связывания:**
- **Источники и обработчики** могут иметь **несколько выходов** (один источник → несколько обработчиков)
- **Получатели** имеют **только один вход** (принимают данные от одного источника)
- Все соединения управляются ядром через ID компонентов

**Примеры:**
```
Один источник → два обработчика:
SignalGenerator → WindowSignalCollector  → WindowFunctionsApplier → FFT  → ChartRenderer
                                           FFT  → ChartRenderer

Множественные паралельные обработчики:
SignalGenerator → WindowSignalCollector → WindowFunctionsApplier  → FFTProcessor    → ChartRenderer
                  ChartRenderer           ChartRenderer             ChartRenderer           ↑ (raw spectre)
                        ↑ (signal slice)         ↑ (signal in window)     ↑ (signal with window func in window)
```

### Сетевое взаимодействие (сокеты)

**Компоненты могут общаться по каналам связи:**
- **Сетевые (TCP/UDP) сокеты** для процессами/машинами взаимодействия
- **Локальные сокеты** для взаимодействия внутри одного процесса
- **Последовательные порты** для взаимодействия по последовательному порту
- **USB порты** для взаимодействия по USB порту

### Режимы запуска

**Графический режим:**
- Запуск с UI (Qt Widgets)
- Визуальная сцепка блоков (drag-and-drop соединения)
- Панель управления компонентами
- Возможность фокусировки на окне компонента через кнопки

**Консольный режим:**
- Запуск без UI
- Быстрая сборка (минимальные зависимости)
- Быстрое подключение к компонентам

### Обработка ошибок

**Ядро должно:**
- Проверять доступность компонентов при запуске
- Автоматически запускать недоступные компоненты
- Ожидать готовности компонентов с таймаутом
- Логировать ошибки подключения и запуска
- Предоставлять детальную информацию об ошибках через callback

**Уровни логирования:**
- `INFO` — информация о запуске/остановке компонентов
- `WARNING` — предупреждения (медленный запуск, временные проблемы)
- `ERROR` — ошибки (не удалось запустить компонент, потеря соединения)

## Детальное описание 5 основных компонентов архитектуры

### 1. Ядро приложения (Core)

**Назначение:**
Ядро — это центральный управляющий компонент приложения, который выступает в роли **клиента сокета** и координирует работу всех остальных компонентов системы. Это главный оркестратор, который принимает решения о том, как должны взаимодействовать источники, обработчики и получатели данных.

**Основные функции:**

1. **Управление жизненным циклом компонентов**
   - Запуск и остановка всех компонентов (источников, обработчиков, получателей)
   - Отслеживание состояния каждого компонента
   - Автоматический перезапуск недоступных компонентов
   - Корректное завершение работы при выключении приложения

2. **Управление соединениями между компонентами**
   - Установка соединений между источниками и обработчиками
   - Установка соединений между обработчиками и получателями
   - Разрыв соединений при необходимости
   - Маршрутизация данных между компонентами

3. **Взаимодействие с сервером агрегации**
   - Подписка на события об изменении доступности компонентов
   - Получение списка активных компонентов и их портов
   - Отслеживание подключения/отключения компонентов в реальном времени

4. **Поддержка двух режимов работы**
   - **Графический режим** — с полноценным UI для визуальной настройки и отображения данных
   - **Консольный режим** — без UI, оптимизирован для быстрой сборки и запуска

5. **Обработка ошибок и логирование**
   - Проверка доступности компонентов при запуске
   - Таймауты соединений
   - Детальное логирование всех операций
   - Предоставление информации об ошибках пользователю

**Применение:**
Ядро используется как основное приложение, которое запускается пользователем. Оно может работать как в графическом режиме (для разработки и отладки), так и в консольном режиме (для быстрого тестирования и интеграции). Ядро — это точка входа в систему, через которую пользователь управляет всеми компонентами.

**Пример использования:**
```
Пользователь запускает приложение в графическом режиме
    ↓
Ядро подключается к серверу агрегации (порт 8212)
    ↓
Ядро получает список активных компонентов
    ↓
Ядро отображает UI с доступными компонентами
    ↓
Пользователь визуально соединяет компоненты (drag-and-drop)
    ↓
Ядро устанавливает соединения между компонентами
    ↓
Данные начинают течь от источника через обработчики к получателям
```

### 2. Сервер агрегации (EventAggregatorServer)

**Назначение:**
Сервер агрегации — это **центральный хаб** системы, который отслеживает доступность и состояние всех компонентов. Это единственный компонент с **статическим портом (8212)**, что позволяет всем остальным компонентам легко его найти при запуске.

**Основные функции:**

1. **Регистрация и отслеживание компонентов**
   - Принимает регистрацию новых компонентов (источников, обработчиков, получателей)
   - Хранит информацию о каждом компоненте (UUID, тип, адрес, порт)
   - Проверяет уникальность UUID — два компонента с одинаковым UUID не могут быть активны одновременно
   - Отслеживает, какой компонент первым зарегистрировался с данным UUID

2. **Мониторинг доступности (Heartbeat)**
   - Получает PING сообщения от компонентов каждые 500 мс
   - Отправляет PONG в ответ
   - Если PING не получен в течение 3 секунд, помечает компонент как недоступный
   - Уведомляет все остальные компоненты об изменении доступности

3. **Публикация событий и состояний**
   - Рассылает уведомления при подключении нового компонента
   - Рассылает уведомления при отключении компонента
   - Рассылает уведомления об изменении статуса компонента
   - Позволяет компонентам подписаться на события конкретных компонентов или всех сразу

4. **Выдача информации о компонентах**
   - По запросу выдаёт список всех активных компонентов
   - Предоставляет адрес и порт каждого компонента
   - Позволяет компонентам узнать, где находится нужный им компонент для прямого подключения

5. **Логирование и мониторинг**
   - Логирует все события подключения/отключения
   - Отслеживает время жизни каждого соединения
   - Предоставляет статистику активности

**Применение:**
Сервер агрегации запускается один раз и работает постоянно. Это критически важный компонент, так как без него система не может функционировать. Все остальные компоненты при запуске сначала подключаются к агрегатору, чтобы зарегистрироваться и получить информацию о других компонентах.

**Пример использования:**
```
Сервер агрегации запускается на порту 8212
    ↓
Источник данных запускается и подключается к агрегатору
    ↓
Агрегатор регистрирует источник и рассылает уведомление
    ↓
Обработчик запускается и подключается к агрегатору
    ↓
Агрегатор регистрирует обработчик и рассылает уведомление
    ↓
Ядро подключается к агрегатору и получает список компонентов
    ↓
Ядро может теперь подключиться к источнику и обработчику напрямую
```

### 3. Источник данных (DataSourceServer)

**Назначение:**
Источник данных — это **сервер**, который **производит или захватывает данные** из внешних источников и предоставляет их другим компонентам. Источник не обрабатывает данные, а только их генерирует или захватывает.

**Основные функции:**

1. **Генерация или захват данных**
   - Генерирует синусоидальные сигналы, шум или другие тестовые данные (SignalGenerator)
   - Захватывает системный аудиовыход через WASAPI (AudioLoopbackSource)
   - Получает данные от микроконтроллера ESP32 по последовательному порту (SerialDataSource)
   - Может захватывать данные из других источников (USB, сетевые потоки и т.д.)

2. **Предоставление информации о доступных потоках**
   - Выдаёт список всех доступных потоков данных, которые может предоставить
   - Описывает характеристики каждого потока (частота дискретизации, разрядность, формат и т.д.)
   - Позволяет клиентам узнать, какие данные они могут получить

3. **Управление подписками и запросами**
   - Позволяет клиентам подписаться на конкретный поток данных
   - Может обслуживать несколько клиентов одновременно (один источник → несколько обработчиков)
   - Отправляет данные только активным подписчикам

4. **Регистрация в агрегаторе**
   - При запуске подключается к серверу агрегации
   - Регистрирует себя с уникальным UUID
   - Отправляет PING каждые 500 мс для подтверждения доступности
   - Слушает уведомления об изменении состояния других компонентов

5. **Управление жизненным циклом**
   - Запуск и остановка захвата/генерации данных
   - Корректное завершение при отключении
   - Освобождение ресурсов (закрытие портов, освобождение памяти)

**Применение:**
Источники данных используются как отправные точки для потока данных. Они запускаются отдельно от ядра и ждут подключения. Ядро или другие компоненты подключаются к источнику, чтобы получить данные. Один источник может обслуживать несколько потребителей одновременно.

**Пример использования:**
```
AudioLoopbackSource запускается и слушает на динамическом порту
    ↓
Подключается к серверу агрегации (порт 8212)
    ↓
Регистрируется с UUID и информацией о себе
    ↓
Ядро получает информацию об AudioLoopbackSource от агрегатора
    ↓
Ядро подключается к AudioLoopbackSource на его динамическом порту
    ↓
AudioLoopbackSource начинает захватывать системный аудио
    ↓
AudioLoopbackSource отправляет захваченные данные ядру
    ↓
Ядро перенаправляет данные обработчикам
```

### 4. Обработчик данных (DataProcessorServer)

**Назначение:**
Обработчик данных — это **сервер**, который **преобразует входные данные в выходные**. Обработчик получает данные от источника или другого обработчика, применяет к ним какую-то трансформацию и отправляет результат дальше.

**Основные функции:**

1. **Преобразование данных**
   - WindowSignalCollector — собирает сигналы в окно размером 2^N для FFT
   - WindowFunctionsApplier — применяет оконные функции (Hanning, Hamming и т.д.)
   - FFT — преобразует сигнал из временной области в частотную
   - AmplitudeSpectrumConversion — преобразует результат FFT в амплитудный спектр
   - EnergySpectrumConversion — преобразует результат FFT в энергетический спектр
   - VolumeNormalization — нормализует громкость по стандарту ISO 226
   - BarkScaleMapper — преобразует частоты в шкалу Bark
   - MelScaleMapper — преобразует частоты в шкалу Mel
   - SpectrogramBuilder — строит спектрограмму из последовательности спектров

2. **Получение данных от источников**
   - Подключается к источнику данных как клиент
   - Получает данные от источника
   - Может подписаться на конкретный поток данных источника

3. **Отправка обработанных данных**
   - Слушает входящие соединения от других обработчиков или получателей
   - Отправляет обработанные данные всем активным подписчикам
   - Может обслуживать несколько потребителей одновременно

4. **Регистрация в агрегаторе**
   - При запуске подключается к серверу агрегации
   - Регистрирует себя с уникальным UUID
   - Отправляет PING каждые 500 мс
   - Получает уведомления об изменении доступности других компонентов

5. **Автоматическое переподключение**
   - Если получатель отключился, обработчик получает уведомление от агрегатора
   - Ожидает восстановления получателя
   - Автоматически переподключается к получателю, когда тот снова доступен
   - Продолжает отправку данных без потерь

**Применение:**
Обработчики данных используются для построения цепочек преобразований. Они могут быть как пассивными (только преобразуют данные при получении), так и активными (запускаются в отдельном потоке). Один обработчик может получать данные от одного источника и отправлять их нескольким получателям или другим обработчикам.

**Пример использования:**
```
FFT обработчик запускается и слушает на динамическом порту
    ↓
Подключается к серверу агрегации (порт 8212)
    ↓
Регистрируется с UUID
    ↓
Подключается к WindowSignalCollector как клиент
    ↓
Получает окна сигналов от WindowSignalCollector
    ↓
Применяет FFT преобразование
    ↓
Слушает входящие соединения от других компонентов
    ↓
Отправляет результаты FFT всем подключённым потребителям
    ↓
Если потребитель отключился, получает уведомление от агрегатора
    ↓
Автоматически переподключается при восстановлении потребителя
```

### 5. Получатель данных (DataSinkServer)

**Назначение:**
Получатель данных — это **сервер**, который **потребляет данные** для различных целей: отображения, записи, воспроизведения или дальнейшей обработки. Получатель — это конечная точка потока данных.

**Основные функции:**

1. **Приём и обработка данных**
   - ChartRenderer — отображает данные на 2D графике
   - SpectrogramRenderer — отображает 3D спектрограмму
   - AudioRenderer — воспроизводит аудио через устройство (в будущем)
   - DataRecorder — записывает данные в файл (в будущем)

2. **Управление входящими соединениями**
   - Слушает входящие соединения от обработчиков или источников
   - **Принимает только одно соединение** (в отличие от источников и обработчиков)
   - Отклоняет дополнительные попытки подключения

3. **Отслеживание состояния входящего потока**
   - Отслеживает, активен ли поток данных
   - Отслеживает, занят ли получатель обработкой данных
   - Выдаёт информацию о своём состоянии другим компонентам

4. **Регистрация в агрегаторе**
   - При запуске подключается к серверу агрегации
   - Регистрирует себя с уникальным UUID
   - Отправляет PING каждые 500 мс
   - Получает уведомления об изменении доступности других компонентов

5. **Управление жизненным циклом**
   - Запуск и остановка приёма данных
   - Корректное завершение при отключении
   - Освобождение ресурсов (закрытие окон, освобождение памяти)

**Применение:**
Получатели данных используются как конечные точки потока данных. Они отображают результаты обработки пользователю или сохраняют их для дальнейшего анализа. Каждый получатель может принимать данные только от одного источника/обработчика, но один источник/обработчик может отправлять данные нескольким получателям.

## Взаимодействие между компонентами

**Типичный сценарий:**

1. **Инициализация системы**
   - Ядро запускается первым и может останавливать, запускать все компоненты, в том числе и сервер агрегации. Если он не запущен - запускает его. 
   - Сервер агрегации запускается на порту 8212
   - Ядро проверяет, что сервер агрегации запустился, и когда это происходит запускает серверы данных.
   - Запущенные серверы данных запускаются и подключаются к агрегатору
   - Ядро получает данные по всем компонентам и настраивает связи и потоки данных

2. **Установка связей обработки данных**
   - Ядро устанавливает соединение между источником и обработчиком
   - Ядро устанавливает соединение между обработчиком и получателем
   - Все соединения управляются ядром через ID компонентов

3. **Передача данных**
   - Когда цепочка настроена, ядро перенаправляет данные из одного канала в другой
   - Источник генерирует/захватывает данные и передает ядру
   - Обработчик получает данные от ядра, преобразует их и передает ядру
   - Получатель получает обработанные данные от ядра и отображает их

4. **Обработка отключений**
   - Если компонент отключился, агрегатор уведомляет ядро
   - Ядро получает уведомление и отключает временно цепочку, при этом все остальные цепочки работают как положено.
   - Как только агрегатор сообщает о восстановлении компонента, ядро переподключается и возобновляет взаимодействие и прием/передачу данных.
   - Источники, обработчики, получатели автоматически переподключаются при восстановлении

5. **Завершение работы**
   - Ядро может останавливает все компоненты
   - Компоненты отключаются от агрегатора
   - Ядро проверяет что отключились все и отключает агрегатор (если это требуется)
   - Ядро завершает работу


## Архитектурные паттерны и принципы проектирования

### Принципы SOLID

Архитектура следует принципам SOLID для обеспечения гибкости, масштабируемости и поддерживаемости:

#### 1. Single Responsibility Principle (SRP)
**Принцип единственной ответственности**

Каждый компонент имеет одну причину для изменения:
- **Источники данных** отвечают только за захват/генерацию данных
- **Обработчики данных** отвечают только за преобразование данных
- **Получатели данных** отвечают только за потребление данных
- **Сервер агрегации** отвечает только за отслеживание доступности и публикацию событий
- **Ядро** отвечает только за управление жизненным циклом и соединениями

**Применение:** Каждый класс должен иметь одну четко определённую ответственность. Например, класс `WindowSignalCollector` отвечает только за сбор сигналов в окно, а не за применение оконной функции.

#### 2. Open/Closed Principle (OCP)
**Принцип открытости/закрытости**

Компоненты открыты для расширения, но закрыты для модификации:
- Новые типы обработчиков добавляются без изменения существующего кода
- Новые типы визуализаций добавляются без изменения ядра
- Новые источники данных добавляются без изменения системы

**Применение:** Использование интерфейсов и абстрактных классов позволяет добавлять новые реализации без изменения существующего кода.

#### 3. Liskov Substitution Principle (LSP)
**Принцип подстановки Лисков**

Все реализации интерфейса должны быть взаимозаменяемы:
- Любой источник данных может быть заменён на другой без изменения кода
- Любой обработчик может быть заменён на другой
- Любой получатель может быть заменён на другой

**Применение:** Все источники наследуют от `IDataSource`, все обработчики от `IDataProcessor`, все получатели от `IDataSink`.

#### 4. Interface Segregation Principle (ISP)
**Принцип разделения интерфейса**

Клиенты не должны зависеть от интерфейсов, которые они не используют:
- Интерфейсы разделены по функциональности (захват, обработка, отображение)
- Каждый компонент реализует только необходимые интерфейсы
- Нет "толстых" интерфейсов с ненужными методами

**Применение:** Отдельные интерфейсы для разных типов обработчиков (сигнальные обработчики, визуализаторы и т.д.).

#### 5. Dependency Inversion Principle (DIP)
**Принцип инверсии зависимостей**

Зависимости должны быть от абстракций, а не от конкретных реализаций:
- Ядро зависит от интерфейсов, а не от конкретных компонентов
- Компоненты зависят от интерфейсов, а не друг от друга
- Инъекция зависимостей через конструкторы или фабрики

**Применение:** Использование интерфейсов для всех взаимодействий между компонентами.

### Паттерны Gang of Four

#### Creational Patterns (Порождающие паттерны)

**1. Factory Method / Abstract Factory**
- **Применение:** Создание различных типов источников, обработчиков и получателей
- **Проблема:** Разные типы компонентов требуют разных способов инициализации
- **Решение:** Фабрики для создания компонентов по типу (SignalGeneratorFactory, AudioLoopbackSourceFactory и т.д.)

**2. Singleton**
- **Применение:** Сервер агрегации (единственный экземпляр на всю систему)
- **Проблема:** Нужна единая точка доступа к агрегатору
- **Решение:** Singleton для EventAggregatorServer

**3. Builder**
- **Применение:** Конфигурация сложных компонентов (например, цепочка обработчиков)
- **Проблема:** Компоненты могут иметь много параметров конфигурации
- **Решение:** Builder для пошагового построения конфигурации

#### Structural Patterns (Структурные паттерны)

**1. Adapter**
- **Применение:** Адаптация различных источников данных к единому интерфейсу
- **Проблема:** Разные источники имеют разные API (WASAPI, Serial Port, Generator)
- **Решение:** Адаптеры для преобразования разных API к IDataSource

**2. Decorator**
- **Применение:** Добавление функциональности к обработчикам без изменения их кода
- **Проблема:** Нужно добавлять логирование, кэширование, профилирование к обработчикам
- **Решение:** Декораторы для оборачивания обработчиков дополнительной функциональностью

**3. Facade**
- **Применение:** Упрощение взаимодействия с системой компонентов
- **Проблема:** Ядро должно управлять множеством компонентов и соединений
- **Решение:** Фасад (Core) предоставляет простой интерфейс для управления всеми компонентами

**4. Proxy**
- **Применение:** Отложенная инициализация компонентов, контроль доступа
- **Проблема:** Компоненты могут быть недоступны при запуске
- **Решение:** Прокси для отложенного подключения к компонентам

**5. Composite**
- **Применение:** Построение цепочек обработчиков как единого целого
- **Проблема:** Нужно обрабатывать как отдельные обработчики, так и цепочки
- **Решение:** Composite для представления цепочек как единого обработчика

#### Behavioral Patterns (Поведенческие паттерны)

**1. Observer**
- **Применение:** Подписка на события изменения доступности компонентов
- **Проблема:** Компоненты должны реагировать на события от агрегатора
- **Решение:** Observer для подписки на события (компонент подключился, отключился и т.д.)

**2. Strategy**
- **Применение:** Различные стратегии обработки данных (FFT, Bark Scale, Mel Scale и т.д.)
- **Проблема:** Разные обработчики используют разные алгоритмы
- **Решение:** Strategy для инкапсуляции различных алгоритмов обработки

**3. State**
- **Применение:** Управление состояниями компонентов (инициализация, работа, ошибка, отключение)
- **Проблема:** Компоненты имеют разные состояния и переходы между ними
- **Решение:** State Machine для управления состояниями компонентов

**4. Command**
- **Применение:** Команды для управления компонентами (запуск, остановка, переподключение)
- **Проблема:** Нужно отправлять команды компонентам через сеть
- **Решение:** Command для инкапсуляции команд в объекты

**5. Mediator**
- **Применение:** Координация взаимодействия между компонентами через ядро
- **Проблема:** Компоненты не должны знать друг о друге напрямую
- **Решение:** Mediator (Core) для управления взаимодействием между компонентами

**6. Chain of Responsibility**
- **Применение:** Цепочка обработчиков, где каждый обработчик может передать данные следующему
- **Проблема:** Данные должны проходить через цепочку обработчиков
- **Решение:** Chain of Responsibility для построения цепочек обработки

### Рекомендуемые паттерны для расширения

| Сценарий расширения | Рекомендуемый паттерн | Причина |
|-------------------|----------------------|---------|
| Добавление нового типа источника | Factory Method + Adapter | Упрощает создание и адаптацию новых источников |
| Добавление нового типа обработчика | Strategy + Decorator | Позволяет добавлять новые алгоритмы без изменения кода |
| Добавление нового типа визуализации | Factory Method + Composite | Упрощает создание и комбинирование визуализаций |
| Логирование и профилирование | Decorator + Observer | Добавляет функциональность без изменения компонентов |
| Кэширование результатов | Proxy + Decorator | Оптимизирует производительность |
| Обработка ошибок и восстановление | State + Chain of Responsibility | Управляет состояниями и обработкой ошибок |
| Конфигурация компонентов | Builder + Factory Method | Упрощает создание сложных конфигураций |
| Тестирование компонентов | Mock Objects + Adapter | Позволяет тестировать компоненты изолированно |
